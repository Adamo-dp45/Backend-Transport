    > !! `skip_null_values: false` dans le `normalization_context` par DÉFAUT (`api_platform.yaml`) : un champ nul est SÉRIALISÉ à null au lieu d'être OMIS de la charge. Par défaut `ApiPlatform` le retire, et le FT tournant en `strict_variables`, `{{ gare.contact2 }}` levait « Key "contact2" ... does not exist » dès qu'un second contact n'était pas renseigné — une 500 qui n'apparaît QUE sur les enregistrements incomplets, donc jamais chez le développeur et toujours chez le client. Vérifié sur l'ensemble des pages avec tous les champs optionnels vidés — rien ne casse aujourd'hui, mais c'est le piège à connaître en écrivant un nouveau gabarit

    > !! bloquer la connexion aux utilisateurs suspendus on a `UserChecker`, vu que le `checker` ne bloque pas un utilisateur suspendu qui a déjà un `jwt token` valide ou qui est connecté ce qui lui permet de faire des requêtes api après avoir été suspendu pour ça on utilisé l'évènement `lexik_jwt_authentication.on_jwt_authenticated` de `lexikBundle` qui se déclanche quand un `jwt` valide est présenté sur une requête, dans `JWTSubscriber` va vérifié à chaque requête authentifiée si il y'a un `jwt` existant pas sur toutes les requêtes

    > !! récupérer la collection de `personnel` pour `voyages` et `depannages` on n'a un cas différent vu qu'il ne sont pas directement liées mais via `Detailpersonnel`, on a 3 approches

        > Gestion des comptes utilisateurs et de l'entreprise

        > Gestion des permissions RBAC
        > !! l'INSCRIPTION n'est PAS publique : `POST /api/register` est en `security: ROLE_SUPER_ADMIN`. Ouverte, cette route laissait n'importe qui créer une entreprise et s'y nommer `ROLE_ADMIN` — donc s'ouvrir un périmètre complet. C'est l'exploitant de la plateforme qui enregistre une compagnie ET son administrateur FONDATEUR (`isFounder`, `ROLE_ADMIN`, entreprise + slug public créés dans la même transaction par `RegisterProcessor`). Côté FT c'est `/admin/entreprises/nouvelle` (`EntrepriseController::new`, `ROLE_SUPER_ADMIN`), bouton « Nouvelle compagnie » sur le listing des entreprises ; l'ancienne page publique `/inscription` et son `RegisterController` sont supprimés, le lien « S'inscrire » retiré de la connexion
            > La case « j'accepte les conditions » a sauté du `RegisterFormType` : ce n'est plus le futur utilisateur qui remplit le formulaire mais l'exploitant, accepter pour un tiers n'a aucune valeur — et le champ portant `IsTrue`, le garder sans l'afficher rendait le formulaire insoumettable
            > `RegisterProcessor` ne lit JAMAIS l'entreprise de l'ACTEUR (le super admin n'en a pas) : il n'y avait donc rien d'autre à adapter en verrouillant la route
        > !! le TOUT PREMIER super admin ne peut naître d'aucun appel HTTP (puisque `/api/register` en exige déjà un) : il se crée en console, cf. `app:creer-super-admin`
        > Hiérarchie de gestion des comptes (via `UserManagementGuard`) : nul ne se gère soi-même (profil dédié) ; le FONDATEUR gère tous les comptes de SA compagnie, administrateurs compris (c'est lui qui les promeut et les rétrograde) ; le fondateur lui-même n'est géré que par le super admin, les autres admins entreprise par le fondateur ou le super admin ; un agent rattaché à une gare ne gère que les utilisateurs simples de SA gare (jamais un admin de gare) ; un utilisateur central sans gare gère tout le monde sauf les admins ; le super admin est protégé (ni suspension ni modification, même par un autre super admin)

    > Le module `Système` (super admin) : Maintenance, Corbeille
        > Mode maintenance GLOBAL de la plateforme (singleton, hors périmètre entreprise) piloté par le super admin : quand il est actif, seul le super admin accède à l'application ; tous les autres voient une page de maintenance
        > Verrou DUR côté interface FT ET côté API (BK) via `MaintenanceSubscriber` (kernel.request) : les requêtes non-super-admin renvoient 503, sauf whitelist (login/refresh/logout, `/api/me`, lecture de l'état) ; fail-open si l'état ne peut pas être lu (on n'enferme jamais à cause d'un hoquet)
        > CORBEILLE multi-entreprises (`Corbeille` ressource virtuelle non persistée, `CorbeilleService` + `CorbeilleRegistry`) : le super admin (HORS périmètre entreprise) voit et gère les enregistrements SOFT-DELETÉS (`deletedAt IS NOT NULL`) de TOUTES les compagnies. Le super admin échappant à `EntrepriseScopeExtension` (ni filtre `identreprise` ni `deletedAt IS NULL`), la corbeille requête en direct (QueryBuilder) SANS scope ; le service ne dépend JAMAIS de l'entreprise de l'ACTEUR (le super admin n'en a pas — piège du provider-avant-security évité, cf. `MeProvider`), l'entreprise affichée est celle de CHAQUE élément (`getIdentreprise` → libellé via `EntrepriseRepository`)
        > Types DÉCOUVERTS automatiquement (aucune MAP à maintenir) : toute entité `EntityBase` (donc `deletedAt`) ET `EntrepriseOwnedInterface`, MOINS une liste d'exclusion documentée (journaux `Activite`/`Alerte`, lecture seule `Inventaire`, détails `Detail*`, singletons de config `Config*`/`ParametreReservation`/`Maintenance`, dérivé/opt-in `ProgrammeFidelite`/`Beneficiaire`) → 27 types. Le `type` d'URL est le nom court en minuscules (`ticket`, `gare`…)
        > Actions COMPLÈTES : restaurer (`setDeletedAt(null)`) / supprimer définitivement (unitaire), et EN LOT « tout restaurer » / « tout vider » — toutes filtrables par `type` + `entreprise`. Purge protégée contre les contraintes FK (`ForeignKeyConstraintViolationException` → 422 lisible) ; le vidage en lot est TRANSACTIONNEL (tout ou rien). Facettes STABLES : `parType` (compté pour l'entreprise sélectionnée) et `parEntreprise` (global) N'appliquent PAS le filtre de type, sinon les autres options disparaîtraient ; seuls les `items` sont filtrés (limités par type). Audit `ActiviteLogger` volontairement NON branché ici (il exige l'entreprise de l'acteur, absente pour le super admin)
        > API (`security: ROLE_SUPER_ADMIN`) : `GET /api/corbeille` (compteurs + éléments, `?type[]=&entreprise=`), `PATCH /api/corbeille/{type}/{id}/restaurer`, `DELETE /api/corbeille/{type}/{id}`, `POST /api/corbeille/restaurer-tout`, `POST /api/corbeille/vider` (les lots en `Post` car une route statique sans variable est confondue avec la collection). FT : `/admin/systeme/corbeille` (React `CorbeilleTable`, filtres + actions POST/CSRF), entrée de menu « Corbeille » réservée au super admin

    > Le module `Exploitation` : Gare, Ligne, Arret, Tarif, Voyage
        > Gestion des gares
        > Une `Ligne` est un itinéraire ordonné d'arrêts (`Arret` = Gare + ordre) : 1er arrêt = origine, dernier = terminus, les autres sont intermédiaires. (Remplace l'ancien `Trajet`)
        > Chaque arrêt porte `dureeTronconMinutes` (durée du TRONÇON qui mène à lui, depuis l'arrêt précédent ; NULL à l'origine, > 0 ensuite ; facultative mais TOUT-OU-RIEN). L'HEURE DE PASSAGE prévue du car à un arrêt est la SOMME des tronçons de l'origine effective jusqu'à lui (`ReservationEcheanceService::heurePassage`), ajoutée à `datedepartprevue` — le cumul n'est PAS stocké, il est recalculé. Sur elle se calent les échéances de réservation. Saisir par tronçon donne aussi le temps de trajet théorique de chaque segment. Le décalage est RELATIF À L'ORIGINE EFFECTIVE DU VOYAGE, pas à celle de la ligne : sur un DÉPART PARTIEL (Bouaké crée un voyage Abidjan → Korhogo), `datedepartprevue` est l'heure de Bouaké, donc Bouaké passe à l'heure annoncée et Korhogo à `+ (somme des tronçons de Bouaké à Korhogo)`. Non renseignée, tout retombe sur le départ du voyage (comportement historique)
        > RECALAGE (`RecalageService`, `GET /api/lignes/{id}/recalage`, admin) : les `dureeTronconMinutes` sont saisis à la main et vieillissent, faisant dériver TOUT le calcul (heures de passage, échéances, retards) SANS le dire. Le service compare, tronçon par tronçon, le déclaré à la MÉDIANE réellement observée sur les passages (médiane, pas moyenne : une panne isolée ne déplace pas l'horaire). Mesure d'un tronçon = temps réel à l'arrêt − temps réel à l'arrêt précédent (arrivée horodatée, ou départ réel à l'origine) : c'est EXACTEMENT la construction de `heurePassage`, donc recaler ramène le retard médian à zéro. PROPOSE seulement — appliquer déplace les heures annoncées (donc les échéances des réservations en cours), c'est une décision d'exploitation VALIDÉE À LA MAIN via le formulaire de ligne (bouton « Appliquer » par tronçon + « Tout appliquer », puis enregistrement normal). Un tronçon n'est proposé qu'au-delà de `?minObservations` (défaut 3) : à faible couverture de pointage (cf. `qualiteDonnee`), les suggestions ne sont pas fiables — les deux notions sont liées
        > La grille `Tarif` est GLOBALE par entreprise : un prix par couple de gares (garedepart → garearrivee), saisi une seule fois et partagé par toutes les lignes, avec création automatique du sens inverse au même montant. (Remplace l'ancien tarif par ligne `TarifLigne`)
        > Un `Voyage` est une instance d'une `Ligne` à une date donnée (provenance/destination dérivées de la ligne)
            > Affecter un car disponible et du personnel via détail personnel à un voyage
            > Gérer horaires de départ et d'arrivée
            > NUMÉRO DE DÉPART DU JOUR (`Voyage::$numerodepart`, `NumeroDepartService`) : « DÉPART 4 », la case que le passager lit sur son billet face à son siège. Compteur par ENTREPRISE + LIGNE + GARE DE PROVENANCE effective + JOUR — le Nième car que CETTE gare lance sur CETTE ligne ce jour-là. Un DÉPART PARTIEL tient donc sa PROPRE suite : à Bouaké, le premier car de la journée s'annonce « départ 1 » même si Abidjan en a déjà fait partir deux sur la même ligne. C'est la lecture du GUICHET — le passager entend l'ordre des cars que SA gare fait partir, et son billet porte déjà sa destination. À ne pas confondre avec `codevoyage` (`{codeligne}-V{n}`), qui identifie le voyage pour l'exploitation et ne se remet jamais à zéro
                > FIGÉ à la création, sous VERROU sur la ligne et dans la transaction d'écriture (`VoyageProcessor`) : un départ ouvert APRÈS coup pour une heure plus tôt portera quand même un numéro plus grand — conséquence assumée, le prix de la STABILITÉ DE L'IMPRIMÉ. Un billet remis au client ne doit jamais changer de numéro dans son dos ; l'ordre chronologique, lui, se lit sur l'heure, qui est imprimée juste au-dessus
                > SEULE exception, le changement de JOUR (replanification) : le numéro appartient à une JOURNÉE, le garder ferait deux « Départ 1 » le jour d'accueil — et l'index unique refuserait l'écriture. Il est donc repris dans la nouvelle journée et AUDITÉ (`ActiviteLogger::VOYAGE_NUMERO_DEPART`), le numéro étant déjà imprimé sur des billets. Un simple décalage d'horaire (7 h → 9 h) ne touche à rien
                > !! le compteur lit le plus haut numéro EN INCLUANT LES VOYAGES SUPPRIMÉS (`VoyageRepository::maxNumeroDepart`, aucun `deletedAt IS NULL`) : un départ mis en corbeille garde sa ligne en base, donc son numéro et sa part de l'index. L'exclure rendrait son numéro au suivant — le défaut corrigé sur `codeticket`, dont le générateur comptait les non-supprimés
                > !! `jourdepart` (jour de `datedepartprevue`, maintenu par SON SETTER) est un DÉRIVÉ STOCKÉ, contre la règle maison, pour une seule raison : porter l'unicité par un INDEX déclaré DANS LE MAPPING. Une expression (`CAST(datedepartprevue AS DATE)`) ne s'y déclare pas, donc n'existerait pas dans la base de TEST — construite par `doctrine:schema:update` (cf. `make test-db`) et non par les migrations : les tests auraient validé une règle que la production seule aurait tenue. Migration `Version20260922110000`, verrouillé par `tests/Api/NumeroDepartTest.php`
        > Droits par position de gare sur le voyage (via `VoyageGuard`) : « l'ORIGINE prépare · l'INTERMÉDIAIRE réceptionne · le TERMINUS clôture ». On distingue la PLANIFICATION de l'EXPLOITATION
            > Planification / propriété (créer, modifier, affecter le commercial, supprimer) via `assertPeutPlanifier` : uniquement la gare d'ORIGINE effective (= `gareprovenance` sur un départ partiel), ou un admin / un utilisateur central sans gare. Une gare intermédiaire ne prépare pas, elle réceptionne
            > Exploitation / incident (affecter ou changer le car, le chauffeur / personnel) via `assertPeutGerer` : toute gare de la ligne SAUF la destination, pour que la gare où se trouve réellement le car puisse intervenir (ex: panne en route) ; une gare située AVANT la provenance effective n'intervient pas
            > CHANGEMENT DE CAR → les billets SUIVENT le nouveau véhicule (`ReaffectationSiegeService`, appelé par `AffectcarProcessor` ET le PATCH `VoyageProcessor`) : les sièges appartiennent au CAR, pas au voyage. On REPREND le même numéro s'il existe dans le nouveau car, sinon on RASSOIT le passager sur un siège LIBRE de son tronçon (ordre de montée) — en cas de panne l'exploitation veut faire monter TOUT LE MONDE, quitte à changer le numéro de siège. La REVENTE (tronçons disjoints) est préservée (recollée sur un même siège), un CONFLIT préexistant est résolu (siège propre à chacun). REFUS fail-closed s'il ne reste aucun siège libre sur un tronçon. Sans ce rattachement, un billet garderait un siège de l'ANCIEN car — invisible du plan (`SiegeStateProvider`) et de l'occupation (`CapaciteService`), sa place revendue une seconde fois. NB : le PATCH voyage n'a pas d'autre garde de capacité, c'est ce refus qui la porte
            > Création `assertPeutCreerDepart` : un agent lance le départ depuis SA gare (qui doit être un arrêt de la ligne et non le terminus) ; si sa gare = origine de la ligne c'est un départ normal, sinon c'est un DÉPART PARTIEL. Un admin / utilisateur central part de l'origine de la ligne
            > Clôture : uniquement la gare de DESTINATION (terminus) ou un admin ; un voyage clôturé n'est plus modifiable ni affectable
            > Réception `/voyages/{id}/receptionner` : uniquement une gare INTERMÉDIAIRE (ni provenance ni terminus) ; bascule automatiquement les courriers (`EN_TRANSIT → RECEPTIONNE`) et bagages (`EMBARQUE → LIVRE`) qui y descendent, et clôt les réservations dont la gare de montée vient d'être dépassée
            > !! ORDRE DES RÉCEPTIONS (`VoyageGuard::assertPeutReceptionner`) — une gare ne réceptionne QUE si tous les arrêts situés entre l'origine effective et elle portent une ARRIVÉE horodatée. Ce n'était pas gardé, et ça ne coûtait pas qu'un horodatage : la réception AVANCE la position du car, donc Bouaké réceptionnant avant que le car n'atteigne Yamoussoukro fermait d'un coup, POUR YAMOUSSOUKRO, les réservations vivantes (place rendue, paiement clos, cliente à reloger), la vente de billets, leur correction, les désistements et l'émission d'un billet de réservation — et le départ disparaissait même de son sélecteur, sans le moindre message. Le tout SANS RETOUR EN ARRIÈRE : `garecourante` n'est pas écrivable par l'API et n'avance que dans un sens
                > Le pointage recherché est l'ARRIVÉE dans `Passage`, pas une réception : l'avance déclarée par le COMMERCIAL à bord (`AvanceePositionService`) suffit donc. Une gare traversée sans agent — le cas ordinaire — ne bloque pas la suivante
                > RATTRAPAGE `PATCH /voyages/{id}/rattraper-passage` (`ROLE_ADMIN`, `RattraperPassageProcessor`) : la porte de sortie quand personne n'a pointé, sans quoi un oubli bloquerait toute la ligne derrière lui. Elle CONSIGNE UN PASSAGE, elle NE RÉCEPTIONNE PAS : les courriers et bagages qui descendent là ne basculent pas — s'il n'y avait personne pour pointer le car, il n'y avait probablement personne pour décharger. La gare fera sa réception ensuite (l'arrivée déjà posée n'est pas réécrite, seuls les colis basculent)
                > L'HEURE RÉELLE est OBLIGATOIRE et doit s'INSÉRER entre les passages déjà connus (postérieure au départ ou au passage amont, antérieure au passage aval, et jamais dans le futur). Prendre l'instant de la correction rouvrirait par la porte de service le défaut que la garde vient de fermer : tronçon mesuré négatif, retard de la gare égal à celui de l'oubli — et cette fois signé par un administrateur, donc au-dessus de tout soupçon. Le départ du voyage doit être enregistré au préalable, sinon le passage rattrapé lui serait antérieur
                > Audité à part (`ActiviteLogger::VOYAGE_PASSAGE_RATTRAPE`) : c'est une écriture RÉTROACTIVE sur la chronologie d'un voyage. L'avance de position elle-même est partagée avec la réception (`PositionCouranteService`) — deux chemins, un seul état possible. Verrouillé par `tests/Api/ReceptionOrdreTest.php`
                > MÊME GARDE sur la voie du COMMERCIAL (`AvanceePositionService`) : on n'avance pas par-dessus un arrêt jamais pointé. Elle ne coûte RIEN à `commercialflutter`, qui n'avance que vers `prochainArret` — l'arrêt immédiatement suivant : un saut lui est impossible, en ligne comme hors ligne, et le rejeu d'une file reproduit la même progression pas à pas. Elle attrape donc l'appel direct à l'endpoint, l'admin qui saute un arrêt, un futur client mal écrit
                > !! la chaîne des passages se lit par `PassageService::premierArretNonPointe`, JAMAIS par `Voyage::getPassages()`. `PassageService::pour()` persiste sans flusher ET sans rattacher le passage à la collection du voyage : dans un LOT hors ligne, la deuxième avance ne verrait pas l'arrivée posée par la première et serait refusée au motif qu'elle n'a jamais eu lieu. Même piège, même remède que `connu()` pour le départ après une arrivée
                > !! `PositionCouranteService` (gares) ferme les réservations dépassées, `AvanceePositionService` (commercial) NON. Différence ASSUMÉE : le commercial signale où est le véhicule, la gare CONSTATE son passage — et c'est ce constat, opposable, qui décide qu'un client ne sera pas embarqué. Les fusionner fermerait des réservations sur une simple déclaration de position, y compris rejouée depuis une file hors ligne
        > HORAIRES RÉELS de passage (`Passage`, un enregistrement par voyage×gare, écriture centralisée `PassageService`) : ARRIVÉE horodatée aux points d'exploitation existants (départ origine = `datedepartreelle` ; réception ou avance commercial pour un intermédiaire ; clôture = `datearriveereelle` au terminus) ; DÉPART d'une gare intermédiaire via l'action dédiée `/voyages/{id}/repartir` (RepartirVoyageProcessor : commercial, agent de la gare courante, ou admin). `datedepartreelle`/`datearriveereelle` restent la source pour l'origine/terminus, `Passage` les reflète et ajoute les intermédiaires. Le RETARD (arrivée réelle − heure de passage prévue) et le TEMPS D'ARRÊT (départ − arrivée) sont DÉRIVÉS à la lecture, jamais stockés

            > PRÉVENIR PLUTÔT QUE RELOGER — un siège déjà vendu par une gare AVAL est SIGNALÉ à l'amont (`Siege::$venduAval` + `avalNom`/`avalMontee`/`avalDescente`/`avalNombre`, posés par `SiegeStateProvider` en mode par tronçon). La priorité amont ne bouge pas d'un pouce : le siège reste LIBRE et vendable. Mais la plupart des évictions ne viennent pas d'un car plein — elles viennent d'un siège pris au hasard alors qu'un autre était libre. Prévenir au moment du CHOIX les supprime sans rien changer à la règle

    > Le module `Réservation` : Reservation, ParametreReservation

        > API PUBLIQUE `/api/reservation/*` (multi-tenant via `?slug=`) consommée par les apps mobiles (Flutter + React Native), seuls clients de la réservation : la façade web `WebClientController` est mise en commentaire.
